## How to delete it all

```bash
cd backend
DATABASE_URL="<from infra/.env>" npx ts-node prisma/seed-demo-client.ts --undo
```

The Azure Postgres firewall only allows Azure services, so before running the undo you need a temp rule for your IP, and you should remove it after:

```bash
MYIP=$(curl -s https://api.ipify.org)
az postgres flexible-server firewall-rule create -g clams-rg --name clams-pg-8ca7 \
  --rule-name temp-demo-cleanup --start-ip-address $MYIP --end-ip-address $MYIP
# ...run the --undo above...
az postgres flexible-server firewall-rule delete -g clams-rg --name clams-pg-8ca7 \
  --rule-name temp-demo-cleanup --yes
```

The undo deletes only rows where `worker_code` is one of the 13 below **and** `notes = 'DEMO_CLIENT_2026-07-11'`, plus their attendance sessions. Site assignments and QR credentials cascade automatically. Nothing real is touched.

**Two safety markers**, if you ever want to find these by hand:

- every person has `notes = 'DEMO_CLIENT_2026-07-11'`
- all codes are in a reserved **9xxx band** (`W-9001`–`W-9006`, `S-9001`–`S-9004`, `V-9001`–`V-9003`). Your real records use the 0xxx/1xxx bands, so there is no overlap.

## Two things to expect during the demo

1. **V-9003 (yesterday's visitor) shows as EXITED, not active.** That's correct behaviour, not a bug — visitor passes are day passes, and the nightly job expires any visitor whose visit date has passed. It's a good thing to point out to the client.
2. **The open sessions will age.** If a session stays open past 12 hours the forgot-logout monitor emails and flags it. Demoing today, that's fine. If you demo again on a later day, re-run the undo and re-seed so the times look fresh.
